# Обработка записей, отмен и выручки

## Выбранная схема

Выбран вариант `A`: одна оплата может быть перенесена на новую запись без создания дубликата.

Почему выбрана именно эта схема:
- уже существующая модель `enrollments + payments` подходит под перенос без отдельного второго реестра;
- меньше изменений в CRM и меньше шансов получить рассинхрон между записью, листом ожидания и платежом;
- перенос и возврат можно прозрачно аудировать через отдельный журнал выручки.

## Изменения в базе

### Таблица `payments`

Добавлены поля:
- `enrollment_id uuid references enrollments(id) on delete set null`
- `note text`

Назначение:
- `enrollment_id` хранит, к какой конкретной записи сейчас привязан платеж;
- `note` хранит причину отвязки или переноса, например сохранение оплаты после отмены.

### Таблица `revenue_audit_log`

Поля:
- `id uuid primary key`
- `payment_id uuid`
- `participant_id uuid`
- `enrollment_id uuid`
- `event_id uuid`
- `direction text` (`plus | minus | neutral`)
- `operation_type text`
- `amount_rub integer`
- `reason text`
- `created_at timestamptz`

Назначение:
- хранит все изменения выручки и нейтральные финансовые переносы для аудита;
- позволяет увидеть, было ли это новым платежом, переносом, возвратом или ручной корректировкой.

## Реализованная бизнес-логика

### 1. Новая запись клиента

При создании новой записи система:
- создает `enrollment`;
- ищет уже существующую оплату для этой записи;
- если есть отвязанная сохраненная оплата клиента, переиспользует ее;
- если оплаты нет, создает новую запись в `payments`.

### 2. Перенос клиента на новую дату

При переносе:
- `enrollment.event_id` обновляется на новую дату;
- уже существующая оплата переносится на новую запись;
- новый платеж не создается;
- в `revenue_audit_log` пишется запись `payment_transferred`.

### 3. Отмена с сохранением оплаты

При отмене с сохранением оплаты:
- запись получает статус `Отменена`;
- платеж отвязывается от старого события и старой записи;
- статус платежа не сбрасывается, поэтому выручка не уменьшается;
- в журнал пишется `cancellation_credit_retained`.

### 4. Отмена с возвратом

При полном возврате:
- запись получает статус `Отменена`;
- платеж получает статус `Возврат`;
- сумма вычитается из выручки;
- в журнал пишется `refund_issued`.

### 5. Ручное редактирование оплат

Во вкладке оплат:
- при подтверждении оплаты создается запись в аудите с `plus`;
- при возврате создается запись с `minus`;
- при изменении суммы уже оплаченного платежа логируется дельта.

### 6. Самозапись с сайта

Если клиент повторно записывается на сайте, а у него уже есть сохраненная и отвязанная оплата:
- новая запись создается;
- старый платеж автоматически привязывается к новой дате;
- повторная оплата не создается.

## Изменения в CRM

### Действия по записи

Во всплывающем списке участников занятия доступны:
- `Отметить оплату`
- `Перенести`
- `В депозит`
- `Возврат`

### Оплаты

На странице `/crm/payments` добавлен блок `История выручки`, где видны:
- дата изменения;
- тип операции;
- влияние на выручку;
- сумма;
- участник;
- занятие;
- причина.

## Тестовые сценарии

Проверены сценарии:
- новая запись с уже сохраненной оплатой не создает второй платеж;
- перенос между датами не создает дубликат платежа;
- отмена с сохранением оплаты не уменьшает выручку;
- отмена с возвратом уменьшает выручку один раз;
- ручная корректировка уже оплаченного платежа пишет разницу в журнал;
- webhook Т-Банка обновляет конкретную запись и пишет событие в аудит.
